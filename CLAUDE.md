# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Firmware for the ControlHubAA26 control hub: a NUCLEO-F439ZI (STM32F439ZI, Cortex-M4F)
running FreeRTOS + lwIP, built with STM32CubeIDE 2.2.0 (managed build, GNU Tools for
STM32 14.3.rel1). The repo root holds the git metadata and `README.md`; the CubeIDE
project itself is the nested `ControlHubAA26_V1/` directory, which is also the Eclipse
project root (`.cproject`, `.project`, `ControlHubAA26_V1.ioc`).

`README.md` is the hardware wiring reference — board jumpers, the FTDI serial cable
pinout, the nRF24L01 SPI5 pins, the TC78H611FNG motor connections, and the Norton
firewall rule needed when a Windows machine is the MQTT broker. Consult it before
changing anything pin-related.

## Build

The Debug/Release makefiles are generated by CubeIDE and are gitignored, so they exist
only after the project has been built once. When `ControlHubAA26_V1/Debug/` is present,
build incrementally from a shell (Git Bash) without opening the IDE:

```bash
export PATH="/c/ST/STM32CubeIDE_2.2.0/STM32CubeIDE/plugins/com.st.stm32cube.ide.mcu.externaltools.make.win32_2.2.200.202604021615/tools/bin:/c/ST/STM32CubeIDE_2.2.0/STM32CubeIDE/plugins/com.st.stm32cube.ide.mcu.externaltools.gnu-tools-for-stm32.14.3.rel1.win32_1.0.100.202602081740/tools/bin:$PATH"
cd ControlHubAA26_V1/Debug && make -j8 all     # prints the arm-none-eabi-size summary on success
make clean                                     # full rebuild
```

The plugin directory names carry version stamps and change when CubeIDE is updated —
re-glob `/c/ST/STM32CubeIDE_*/STM32CubeIDE/plugins/*make*` and `*gnu-tools-for-stm32*`
if the paths above no longer resolve.

On a fresh clone (no `Debug/`), the makefiles must be regenerated by CubeIDE first:
either open the project in the IDE, or use `headless-build.bat` in the install root
against the workspace at `~/STM32CubeIDE/workspace_2.2.0`.

There are no tests and no lint step. Flashing and debugging go through CubeIDE /
ST-LINK; the `arm-none-eabi-size` output after a build is the usual sanity check.

**Adding a new source directory requires a `.cproject` edit.** Include paths are listed
there per build configuration (Debug and Release separately) — a new folder under
`Components/` or `Middlewares/` will not be on the include path, and its `subdir.mk`
will not be generated, until it is added. Editing `.cproject` by hand is possible but
error-prone; prefer the IDE's project properties.

## CubeMX regeneration

`ControlHubAA26_V1.ioc` is live — CubeMX regenerates `Core/Src/main.c`, `Core/Src/freertos.c`,
`Core/Src/stm32f4xx_hal_msp.c`, `Core/Src/stm32f4xx_it.c`, `LWIP/`, `FATFS/` and the
`Drivers/` tree. Hand edits in those files survive only inside `/* USER CODE BEGIN x */`
… `/* USER CODE END x */` markers. Anything substantial belongs in the C++ layer instead.

PB8 (motor `/STBY`) is deliberately not claimed in the `.ioc` — `TC78H611FNG_Standby`
configures it at runtime. For the same reason nothing stops a future CubeMX edit handing
PB8 to a peripheral; see the note in `Core/Src/main_tasks.cpp`.

## Architecture

### Boot and the C/C++ boundary

CubeMX-generated code stays C; application code is C++. Two entry points cross the line,
both declared `extern "C"`:

- `initTasks()` (`Core/Src/main_tasks.cpp`) — called from `main()`'s
  `USER CODE BEGIN RTOS_THREADS` block, **before** the scheduler starts. It creates every
  application task, queue, socket and driver object. Anything that must be valid before a
  task can run (transport queues, socket acquisition) is done here synchronously.
- `App_Main()` (`Core/Src/app_main.cpp`) — called from `StartDefaultTask` *after*
  `MX_LWIP_Init()`, i.e. from the lwIP thread context. Anything using the lwIP raw API
  (currently `HTTPD_App_Init()`) must start from here, not from `initTasks()`.

Static C++ constructors run before `main()`, so they must not touch the HAL or the RTOS.

Defining a HAL `__weak` callback from C++ **requires** `extern "C"`. Without it the symbol
is mangled, the weak default stays live, the link succeeds, and the callback silently never
fires. `app_main.cpp` documents this with a worked example.

### SerLink — the framing/transport stack

`Middlewares/SerLink/` is the project's own protocol stack, and the core abstraction of
the codebase. An ASCII frame is:

```
LED01 T   492   002  A1
\___/ |   \_/   \_/  \_/
proto type roll  len  data     ('T' = needs ack, 'U' = fire-and-forget,
(5 ch)               (<=64)     'A' = ack, 'B' = relay ack; ACK_OK = 900)
```

Layers, bottom to top (`Frame` ↔ `Reader`/`Writer` ↔ `Transport` ↔ `Socket`):

- **`Reader`/`Writer`** — `StateMachine` subclasses, each owned by its own task looping on
  `run()`. `Reader` pulls newline-framed strings off a link queue, parses them, sends the
  ack, and posts the frame to a consumer queue. `Writer` serialises outgoing frames and
  waits for their acks.
- **`Transport`** — owned by a task looping on `Transport::run()`. It is the single point
  every frame passes through in both directions: it routes received frames to whichever
  acquired `Socket` matches their 5-character protocol, and forwards outgoing frames to
  the `Writer`. Its dispatch queue is created by the caller and handed in via `init()`.
- **`Socket`** — `transport.acquireSocket("PROTO", receiveCallback, instantHandler)`.
  **`SERLINK_CONFIG__MAX_SOCKETS` is 5** and a sixth acquire returns a silent `nullptr`;
  transport0 is currently full (RAD00, LED01, MOTOR, DBG00, MQTT0).

The two handler kinds matter and are easy to confuse:

- **receive callback** runs in the *Transport* task, after the ack has already gone out —
  so a malformed command is dropped silently, with no way to report it. Use for writes/sets.
- **instant handler** runs in the *Reader* task, before the ack is sent, and its output
  rides back inside the ack frame. Use for reads/queries.

### Two SerLink instances, and the relay

The same stack is instantiated twice:

- **SerLink0** over USART2 (`transport0`, `writer0`/`reader0`, link = `HAL/uart2/`).
- **SerLink1** over the nRF24L01 radio (`transport1`, `writer1`/`reader1`, link =
  `Components/Radio/`), selected by the `RADIO_SERLINK` / `RADIO_TEST_TX` compile-time
  switches at the top of `main_tasks.cpp`. The nRF24L01 driver is not thread-safe, so
  exactly one owner is selected at build time — SerLink1, or one of the raw test tasks.

`SerlinkRelay` bridges a socket on one transport to a socket on the other, in both
directions, keeping the roll code so a source can match the returned relay ack (`'B'`)
to the `'T'` it sent. The LED01 pair is relayed this way: PC → uart2 → radio → remote hub.
All relaying happens in the single task that owns the relay; the Transport tasks only
post to its queue.

`Radio` splits a serialised frame (up to 77 chars) across 32-byte nRF24L01 packets with a
START flag in byte 0, and reassembles on newline — the same framing uart2 uses. All SPI
to the device happens in the one task calling `Radio::run()`; every other method just
posts to `eventQueue`. Channel, data rate and payload size must match the far end exactly
(defaults chosen to match the Arduino RF24 library's own) — a mismatch means silence,
not corruption.

### Hardware drivers

`Components/` holds hardware abstractions used by the application (`Led`, `Button`, `PWM`,
`Motor/TC78H611FNG`, `Motor/L293D`, `nRF24L01`, `Radio`, `Mqtt`). `HAL/` holds thin
per-peripheral C wrappers over CubeMX's handles (`uart2`, `spi5`) that CubeMX does not
generate.

Two shared-state gotchas:

- `PWM` keeps **per-timer** state: all channels on a timer share its prescaler and period,
  so `setFrequency()` retunes every channel on that timer, not just the caller's. The base
  timer is initialised once, by whichever channel calls `init()` first.
- A pin can only be PWM-driven if it appears in `pwmPinMappings[]` in `PWM.cpp`
  (port, pin, timer, channel, alternate function). Adding a PWM pin means adding an entry.

`TC78H611FNG` drives *one* H-bridge channel with **both** IN pins as PWM channels (not one
PWM + one GPIO), so a direction change is two `setPercent()` calls with no pin-mode glitch.
`/STBY` is device-wide and lives in a separate `TC78H611FNG_Standby` shared by both channels.
Bring-up order matters: park the IN pins low, *then* `enable()` standby.

### Networking

Static IP **192.168.0.200** (`LWIP/App/lwip.c`, no DHCP). `MqttPubSub` wraps lwIP's MQTT
client; the broker address is `MQTT_BROKER_IP` in `main_tasks.cpp`. Tasks that touch lwIP
must wait for `netif_is_up(&gnetif) && netif_is_link_up(&gnetif)` — `initTasks()` runs
before `MX_LWIP_Init()`, so the netif coming up is the readiness signal. An lwIP HTTP
server runs from `Core/Src/httpd_app.c`.

## Serial console

USART2 on **PD5 (TX) / PD6 (RX)** via an FTDI cable on CN9 — *not* the ST-LINK virtual COM
port (that is USART3 on PD8/PD9). 115200 baud, CR+LF line ends. Typing a frame into a
terminal is the primary way to drive the board; worked examples for the DBG00, LED01 and
MOTOR sockets are at the top of `Core/Src/main_tasks.cpp`.

## Conventions

- Application code is C++ in `Components/`, `Middlewares/SerLink/` and `Core/Src/*.cpp`;
  everything CubeMX owns stays C.
- No dynamic allocation in the application layer: queues are `xQueueCreateStatic` with
  caller-owned storage, drivers and sockets are file-scope objects in `main_tasks.cpp`.
- Long-running components are `StateMachine` subclasses driven by a `for(;;) x.run();`
  task. The "one owner per driver" rule is enforced by convention and documented in the
  header of each such class — read it before calling a driver from a new task.
- Tuning constants are `#define`s grouped with the object they configure at the top of
  `main_tasks.cpp` (radio channel/payload, MQTT broker/topics/period, motor PWM frequency
  and start percent). Protocol-wide limits live in the `*_config.hpp` files under
  `Middlewares/SerLink/`.
- Header comments in this codebase carry the design rationale — the *why*, the datasheet
  reference, the threading contract. Match that when adding code.
